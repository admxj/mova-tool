# macOS arm64 双轨更新设计

- `vA.B.C`：`A.B` 标识桌面底座。只改 `renderer/` 时同底座递增 `C`；涉及桌面运行时的发布递增 `B` 并将 `C` 归零。第一段升级留待单独确认。两种更新同时存在时独立展示，允许先应用当前底座的界面补丁。
- 客户端分页查询公开 GitHub Releases，分别找同底座的最高已签名界面补丁和更高底座的最新 DMG；不把补丁版号当作已安装桌面版号。DMG 使用已有下载、SHA-256 校验及手动安装流程。
- 前端补丁使用完整 renderer 文件集而不是差量。主进程使用内置 Ed25519 公钥验证清单的原始字节，清单绑定目标版本、底座以及每个文件的路径与完整内容。先验证再加载；限制大小和文件数量，拒绝路径穿越、重复路径及额外文件。不修改 app.asar，不为渲染器增加控制更新的 IPC 权限。
- 补丁在应用数据目录独立暂存和激活。重新加载前提示用户，避免丢失未保存的表单。加载失败回到上一可用界面，必要时回到内置版本；只有新界面报告就绪后才持久化；启动时重新验签并尝试恢复上次已确认的界面。更新状态与桌面底座绑定，升级 DMG 后不会继续加载旧底座补丁。
- GitHub Actions 校验 tag 与包版本一致，并与该底座最近一次发布比较运行时相关文件；未知文件变更按保守规则处理。补丁构建和签名使用专用受保护发布环境的 Secret，签名私钥不进仓库、不进入客户端。DMG 构建沿用 macOS arm64 工作流。第一份支持双轨的版本必须先发 DMG，旧客户端不会凭空获得验签能力。
- 验证：离线覆盖分轨选择、同时可用、版本兼容、篡改、非法路径、失败回滚和 CI 版本边界；用测试密钥和 fixture 在 arm64 Electron 验证重载。不创建真实 Release，除非另行授权。

## 首次发布前配置

1. 在仓库的 GitHub Actions `release` 环境配置 Ed25519 私钥（PKCS#8 PEM）为环境 Secret `TMC_RENDERER_SIGNING_KEY`；同一密钥对的公钥（SPKI PEM）为环境 Variable `TMC_RENDERER_PUBLIC_KEY`。私钥只在受控位置备份，不写入仓库、不粘贴到对话。建议为该环境添加审批和发布 tag 限制。
2. 从 `v1.0.0` 首次升级应先发布 `v1.1.0`：同步更新包版本和 lockfile，待批准后创建 tag。用户需先手动安装新版 DMG；已安装的 `v1.0.0` 不支持自助更新。
3. 后续纯界面改动使用 `v1.1.1` 等同底座 tag。不要直接替换环境公钥：已安装版本只信任内置公钥；换钥需发新桌面底座。

本地离线检查：`node --test test/*.test.js`；macOS Electron 图形验证：`env -u ELECTRON_RUN_AS_NODE ./node_modules/.bin/electron scripts/smoke-renderer-update.js`。
